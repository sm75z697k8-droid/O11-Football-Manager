# Phase 6.9L — Physical, attribute-aware goalkeeper distribution

## User objective and 6.9K limitation

Phase 6.9K correctly spread teammates and regrouped opponents after a real caught shot, but the keeper could still select the nearest apparently available teammate using static distance and lane geometry. That earlier selection did not rehearse the actual throw-ball flight or receiver's possible physical contact. A nominated target 25–40m away was therefore not necessarily a receivable throw.

## Changes and authoritative boundaries

1. **Shared real hand launch model.** `goalkeeperThrowVelocity` in `src/game/physics/goalkeeper-handling.ts` now describes the same horizontal speed `4.8 + 9.3 * power` and launch vertical speed `.4 + 1.2 * power` for the **real command resolver** and the **pure tactical preview**. The real resolver still consumes precisely one seeded aiming-error draw; the preview uses an ideal bearing and consumes **no RNG**. Thus preview never changes real contact, bounce, ball trajectory, or saved seeded replay.
2. **Bounded 50ms physical reception preview.** `src/game/ai/goalkeeper-throw-preview.ts` runs up to 72 of the existing ball physics ticks, receiver turning/acceleration, reactive interception targeting and swept foot-contact checks. It estimates only whether a receiver could get a controllable *nominal* first touch. Opponents have independently estimated interception times along that moving trajectory. Actual defenders and actual receiving players still compete through the unmodified match engine; no interception or completed pass is awarded by the preview. The 72-tick horizon and tactical confidence thresholds are design estimates, not measured football probabilities.
3. **Attributes and real decision trade-offs.** `assessGoalkeeperThrowOptions` tests up to two meaningful launch speeds for each nearby eligible teammate and weighs the preview's physical feasibility, nearby defenders, passing-lane pressure, boundary hazards and throw uncertainty. GK Vision, Decisions and Composure affect perceived opponent risk; Throwing Distribution, Technique and Composure affect expected aim-error tolerance. The actual first-touch and contact outcomes still depend on the receiver's attributes, opponents and seeded real physics.
4. **Realistic bounded waiting.** Keep the established minimum catch hold; preferentially pick a feasible, less threatened receiver, giving the team a short chance to find one. After 78 ticks since catch, pick the best *available* outlet even if the ideal first touch is uncertain. If no teammate comes within the supported throw range at all, after 120 ticks (~6 seconds) launch a genuinely risky, bounded 24m physical throw in the direction of the nearest teammate. This cannot force a completed pass; it only prevents endless hand possession when no outlet arrives.
5. **Both teams and existing features.** The same code is called for a goalkeeper holding a genuine catch on **either side** of the pitch, including away-side mirrored X direction. The 6.9K team positioning remains unchanged. The existing AI pass-intent, 50ms player movement and authoritative goalkeeper throw command still determine the actual action.

## Release verification (GitHub Actions, not iPhone Safari)

- The final GitHub Actions run passed strict TypeScript, **327/327 tests in 53 files**, and a Vite production build.
- Nine new focused goalkeeper throw unit tests cover real swept catches on both sides; physical release/angle/velocity via the real contact resolver from both ends; 50ms non-mutating reception forecast; opponent lane marking and mental-attribute scoring; held-ball delay; indefinite-hold prevention when all teammates are beyond supported range; and a genuine live-seed thrown-ball checkpoint replay.
- The same nine seeded short fictional exhibitions yielded **15 genuine physical shot kicks, 4 goalkeeper catches and 1 genuine goal**, versus Phase 6.9K's **13, 5, 1**. Whole-match intended passing reception was **129/164** versus **129/163** for 6.9K (under 18m: **86/103** versus **86/102**). These differences do not establish a significant attacking improvement.
- **Most importantly, true goalkeeper-throw outcomes:** using the **same new test** on the historical 6.9K engine and the current 6.9L engine, 6.9K completed **5/5 real throws to the intended receiver**, and 6.9L completed **4/4**. The new choices traveled approximately **12.3–22.4m** versus **12.3–17.5m** before; the new system selected generally longer options and made one fewer throw in this short sample. Both achieved 100% in these very small samples; do **not** claim that the new planner improved raw completion rate. The historical comparison ran on a separate pinned commit and its diagnostic PR was closed, never merged. Actual physics decides every outcome.
- Existing goalkeeping, deterministic replay, touchdown/movement tests and simulated seed handling remained intact. The match algorithm version advances to `o11-physical-keeper-throw-preview-p69l-v1`; checkpoint schema remains v9.

## Limitations and next evaluation

The current physical goalkeeper distribution still uses **throws**. There is no distinct underarm roll, driven punt, long aerial kick or configurable keeper distribution tactic. There is no professional goalkeeper training dataset or verified completion likelihood; utility weights are estimates, and opponent interception timing is only an approximate forecast rather than a 22-agent rollout. No official 8-second keeper enforcement, referee warnings or full match restarts are implemented.

The user should load **BUILD 6.9L** on iPhone Safari and watch catches with nearby defenders as well as counterattack opportunities. Pay attention to whether selected receivers reach the actual ball, whether the keeper appears to wait too long, and whether throw distance feels natural. Any new stall can be investigated using the existing Copy Match Debug Report.
